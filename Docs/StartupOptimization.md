# 起動処理の最適化

起動時の追加計測、シェーダー・PSOキャッシュ、テクスチャGPU転送の一括化、通常2D画像の事前変換、Model／Skeleton／Animation間の解析結果共有と永続キャッシュ、アセット一覧探索の共通化、ゲームパッド列挙の非同期化を実装しています。

## シェーダーキャッシュ

コンパイル済みDXILを保存します。キャッシュキーにはコンパイル引数（エントリーポイント・ターゲット・マクロなど）、DXC DLLの内容、作業ディレクトリを含めます。HLSL本体とDXCが実際に読み込んだincludeの内容をSHA-256で検証します。キャッシュの内容も検証し、古い・破損した・読み込めないキャッシュは使わず再コンパイルします。キャッシュ保存に失敗しても、コンパイル結果は利用できます。

リフレクションとマテリアルレイアウト解析は従来どおり実行します。PSOは後述のドライバー用キャッシュも利用します。

ログ例: `[StartupCache] Shaders: hits=119, misses=0`。これはPipelineManagerの初期生成終了時点の件数です。その後に生成される動的パイプラインは、この件数には含まれません。

## PSOキャッシュ

Graphics／Compute PSOの`GetCachedBlob`を`Cache/Startup/PSOs/*.cache`へ保存し、次回は`CachedPSO`として生成APIへ渡します。保存先はプロジェクト直下で、書き込めない場合は既存ContentCacheと同じLOCALAPPDATA配下へフォールバックします。キャッシュが利用できなくても通常生成は続行します。

キーにはシェーダーのバイトコード、シリアライズ済みルートシグネチャ、入力レイアウト、ブレンド・ラスタライザー・深度／ステンシル、出力形式・サンプル数・ノード・フラグ等のPSO記述値と、GPU・取得可能なドライバーバージョン情報を含めます。ポインター値や構造体のパディングはキーに使いません。キー自体が入力内容を表すため、このキャッシュのみ空の外部依存一覧を明示的に許可します。シェーダー等の既存キャッシュの依存ファイル検証は従来どおりです。

キャッシュは内容のハッシュを検証します。破損・不一致は通常生成し、ドライバー更新等で読み込んだPSOがAPIに拒否された場合もキャッシュなしで再試行します。生成成功後にキャッシュを更新します。PSOオブジェクト自体の作成呼び出しやJSON解析・バインディング構築は引き続き必要なので、ヒットしても生成時間が0になるわけではありません。

ログは`[StartupCache] PSOs: hits=..., misses=..., stored=..., rejected=...`と、`[PSOCacheTiming] key=... ms, read=... ms, create=... ms, write=... ms`です。`hits`は保存blobを渡したAPI呼び出しの成功、`rejected`はblob付き呼び出しの失敗、`misses`は通常生成へ進んだ件数です。初期のPipelineManager生成終了時点の累計を出力し、その後の動的生成はこのログに含みません。

`EngineTests/RunPipelineStateCacheRegression.ps1`でGraphics／Computeの再利用、シェーダー・設定・ルートシグネチャ変更、破損・ドライバー拒否からの復旧を確認します。D3D12対応アダプターとVisual Studioのx64開発者PowerShellが必要です。

## ゲームパッド列挙の非同期化

`RegisterDeviceCallback`には`GameInputAsyncEnumeration`を指定し、初回列挙の完了を起動処理で待ちません。デバイス通知前は0台として扱い、通知されたデバイスを既存の排他制御と参照保持を通して次の入力更新へ反映します。キーボード・マウスの初期化順序は従来どおりです。

登録処理の時間は`Input.Controller.AsyncDeviceCallbackRegistration`へ出力します。これは登録APIの時間で、非同期列挙の完了時間ではありません。終了時はコールバックを停止し、登録解除成功後にControllerやデバイス一覧を破棄します。起動直後の接続台数が最終結果であることや、通知前の振動設定が実行されることは保証しません。

## テクスチャの事前変換

対象はPNG、JPEG、BMP、TGA、TIFF、WebPの通常2D画像です。既存と同じRGBA8変換・フィルターで全ミップを生成し、DDSデータとしてキャッシュします。キャッシュを読む場合はミップを再生成しません。元の画像ファイル名・アセットパス・ハンドルの解決方法は変えません。HDR、GIF、既存DDS、キューブマップなどは従来の読み込み経路を使います。

キャッシュがない場合、起動時に従来の読み込みを行ったうえで保存します。そのため初回・画像変更後は変換と保存の時間がかかります。起動前に変換を済ませるには、Developmentビルド後、Visual Studioのx64開発者PowerShellで次を実行します。

```powershell
.\EngineTools\PrepareStartupTextures.ps1 -ProjectPath "C:\path\to\project"
```

指定するフォルダーにはAssetsが必要です。変換ツールは元画像を変更せず、作成済みで有効なキャッシュは再利用します。元画像は初回変換・再生成用に残してください。

キャッシュはプロジェクトの `Cache/Startup/Shaders`、`Cache/Startup/Textures`、`Cache/Startup/Models` に保存します。書き込みできない場合は `%LOCALAPPDATA%/KashipanEngine/StartupCache/<project hash>/` を使います。Assetsの外に置き、アセット監視の対象にしません。これらのフォルダーは削除しても再生成されます。

現在のキャッシュキーは絶対パスを含むため、プロジェクトの移動・別PC・別の配布先では再生成が必要です。今回の変換ツールは指定した配置先向けのものであり、配布パッケージへのキャッシュの自動同梱は行いません。

ログ例: `[StartupCache] Prepared textures: hits=123, misses=0`。非対象形式はこの件数に含まれません。

## GPU転送

TextureManagerの起動時ロードだけをまとめて転送します。転送用メモリの保持量が約64MiBに達したら送信し、最後の残りも送信します。1枚が上限より大きい場合は単独で送信します。転送の準備中は現在の1枚分のメモリも必要です。

各コールバックが転送元・転送先リソースを保持し、GPU完了待ちが終わった後に解放します。白い代替テクスチャは従来どおり先頭へ単独登録します。動的ロード・モデル埋め込み画像は従来の同期転送経路を使います。

ログ例: `[StartupUpload] Textures=123, submissions=24, limit=64 MiB`。白い代替テクスチャはこの件数に含まれません。

## モデル解析の共有

起動時のModelManager生成直前からAnimationManager生成完了まで、同じ物理パスのAssimp解析結果を共有します。モデル用の従来の解析フラグを共通結果に使い、各Managerは必要なデータをコピーします。異なるファイルの並列解析は維持し、同一ファイルへの並列アクセスは1回の解析を待ち合わせます。

Assimp::Importerまたは復元したaiSceneの所有権を共有し、3つのManagerのロード完了後にメモリ上の共有結果を解放します。動的ロードでは共有・永続キャッシュを行わず、各Managerの従来の解析フラグで読み込みます。

解析済みデータは `Cache/Startup/Models/<hash>.cache` へモデルごとに保存します。現在のManagerが使う頂点・法線・接線・UV・面・スキニング・モーフ・ノード階層・変換・マテリアル属性・埋め込みテクスチャ・アニメーションキーを独自バイナリで復元します。Assimpの解析と後処理を省きますが、各Managerのデータ抽出、GPUリソース作成、Prefab／マテリアルの登録処理は引き続き実行します。Assimpの全機能を対象にした汎用シーン交換形式ではありません。現在使っていないカメラ・ライト・メタデータ等を将来Managerが利用する場合は、保存対象とスキーマを更新してください。

元モデルと、Assimpが存在確認・オープンした外部ファイル（glTFの.bin、OBJの.mtl等）を内容ハッシュで検証します。存在しなかった参照先が新しく作成された場合も無効化します。モデルの絶対パス、解析フラグ、Assimpを含むモジュールの内容（静的リンク時はエンジンの実行ファイル）、保存スキーマもキーに含めます。古い・破損したキャッシュは再解析し、保存に失敗しても読み込みは継続します。現在はAssimpを静的リンクしているため、エンジン実行ファイルを更新した場合もモデルキャッシュを再生成します。モデルや外部参照ファイルは削除できません。初回や変更後には保存分の負荷が追加されます。

ログ例: `[StartupCache] Model imports: reused=4, unique=2`、`[StartupCache] Models: hits=2, parsed=0, stored=0`。前者は同じ起動中の共有回数とモデル数、後者はディスク復元・元ファイル解析・保存成功の件数です。

## アセット一覧の共通化

GameEngineが起動時にAssetsを1回だけ再帰探索し、拡張子別の一覧をTexture／Font／BitmapFont／Model／Skeleton／Audio／Animation／Material／Video／Gifの各Managerに渡します。各Manager自身で全フォルダーを再探索しません。既存の拡張子の大文字小文字の区別とファイル順を維持し、GIFはTextureとGif、対応するモデル形式はModel・Skeleton・Animationへ重複して配布します。白い代替テクスチャの先頭登録も維持します。

モデル取り込みが生成した.matは、保存成功時に共通一覧へ追加し、後続のMaterialManagerが同じ起動中に読み込みます。起動時の一覧はManagerの初期化完了後に破棄します。エディターによる実行中の変更監視や明示的な動的読み込みは従来の経路を使います。

ログ例: `[StartupAssets] scans=1, files=882, directories=415`。共通探索は別スレッドで描画初期化と並行して行い、その所要時間を`[StartupTiming] Engine.AssetScan`、結果取得時に残った待ち時間を`Engine.AssetScanWait`へ出力します。各Manager内の一覧受け取り以降は各Managerの区間に出力します。非同期区間の詳しい計測範囲は[StartupTiming.md](StartupTiming.md)を参照してください。

## 追加計測と検証

入力は各デバイスのDLLロード、GameInputCreate、コントローラーの同期列挙を計測します。音声はXAudio2生成、MasteringVoice生成、リバーブバス、Media Foundation初期化、カテゴリ設定を計測します。既存のStartupTimingと同じく、親区間と子区間を足し合わせないでください。起動の累計・完了・中断ログはロガーワーカーでファイルをflushし、起動後にログが静かになっても末尾がバッファに残らないようにしています。

Developmentビルド後、Visual Studioのx64開発者PowerShellで回帰テストを実行できます。

```powershell
.\EngineTests\RunStartupOptimizationRegression.ps1
```

テストには実DXCによるキャッシュ再利用・include／マクロ変更・破損・コンパイル失敗、画像の画素／ミップ一致・元画像変更・保存失敗、GPU転送バッチの寿命保持・分割、モデルの並列共有・動的ロード・実モデルの階層／ボーン比較が含まれます。GPUバッチの回帰テストはスケジューラーのテストであり、GPU上の画素の検証ではありません。

Developmentビルドで、TestプロジェクトをGenerated以下へコピーして測定しました。ソース側のプロジェクトでは実行していません。計測はエンジン入口から初期シーンの最初の描画処理完了までです。

| 項目 | 提供された変更前ログ | キャッシュ利用時の2回の実測 |
|---|---:|---:|
| 起動全体 | 15.169秒 | 8.708〜8.864秒 |
| テクスチャ全体 | 4.312秒 | 1.445〜1.524秒 |
| 画像デコード・ミップ生成／キャッシュ読み込み | 2.923秒 | 0.514〜0.515秒 |

| モデル・スケルトン・アニメーション合計 | 4.213秒 | 1.372〜1.422秒 |

キャッシュ利用時は初期シェーダー119件と対象画像123枚がヒットしました。起動時の画像転送は123枚を24回に分割しました（代替テクスチャは別）。モデル2ファイルは各1回解析し、Skeleton／Animationの合計4回を共有しました。

エンジンのシェーダー・画像キャッシュを削除した測定では12.395秒でした。OSのファイルキャッシュは削除していないため、PC再起動直後の完全なコールド起動を表す値ではありません。変換ツールは最初の実行で123枚を変換し、次の実行では123枚を再利用、両方とも失敗0でした。

追加計測では、入力のコントローラー同期列挙に0.96〜0.98秒、音声のMasteringVoice生成に0.46〜0.48秒を要していました。入力・音声について今回行ったのは計測追加であり、動作変更はしていません。

現時点では5秒以内を達成していません。上表は提供ログとの参考比較であり、同一条件の変更前／変更後を連続実行した厳密なA/B測定ではありません。GPUの描画結果の画素・見た目、Play／Stopなどのエディター操作、正常終了経路は今回の確認対象に含みません。

確認済み: Developmentビルド、各回帰テスト、キャッシュあり／なしの起動完了ログ、実行ログにError／Criticalがないこと。アニメーションありの合成glTFでも、共有前後のチャンネル・移動キーの一致を確認しています。


モデル永続キャッシュの回帰テストは `PersistentModelCacheRegression.cpp`、一覧の互換性は `AssetFileIndexRegression.cpp` です。前者では初回保存・次回復元、元ファイル／外部.mtl変更、存在しなかった参照先の追加、破損・保存失敗、実モデルの骨／モーフを検証します。`SharedModelImportRegression.cpp` では外部.binを使うアニメーションの復元と変更検出も検証します。一覧テストは10種類の順序・日本語パス・生成.mat・Test／JobHuntingGameの実アセットを比較します。


## 2026-10-16のモデルキャッシュ・共通探索の確認結果

Developmentビルドと7種類の起動最適化回帰テストが成功しました。Testプロジェクトの検証用コピーを使用し、別プロセスで初回保存と次回起動での再利用を確認しています。

|---|---:|
| 共通探索（882ファイル・415ディレクトリー） | 0.087秒、ログ上1回 |
| ModelManager | 0.616〜0.632秒 |
| SkeletonManager | 約0.002秒 |
| AnimationManager | 約0.001秒未満 |
| 起動全体 | 7.053〜7.105秒 |

初回は `Models: hits=0, parsed=2, stored=2`、次回以降は `hits=2, parsed=0, stored=0` でした。同じ起動中の共有は `reused=4, unique=2` です。保存された2モデルのキャッシュは合計約180MiBでした。初回のモデル区間は2.086秒で、解析・保存を含みます。初回の起動全体は14.088秒でしたが、グラフィックス初期化も初回4.049秒／再利用時1.792〜1.838秒と変動しているため、全体の差をモデルキャッシュだけの効果とは扱いません。以前のビルドとの厳密なA/B比較でもありません。

5秒以内は未達です。GPU上の画素・見た目、エディター操作、正常終了経路は今回の確認範囲に含みません。JobHuntingGameは一覧互換性の回帰テストで使用し、同プロジェクトの起動全体の実測は行っていません。
